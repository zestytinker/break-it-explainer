The coat check that never panics

A hands-on tour of consistent hashing, in six short steps.

You run a website with four cache servers. Every page has to live on exactly one of them, and everyone has to agree which one, without phoning around.

The obvious rule: scramble the page's name into a number, divide by 4, and the remainder picks the server. Simple. It works right up until the day you add a fifth server. Now you divide by 5 instead, almost every remainder changes, and almost every page is suddenly on the wrong machine. Your caches are empty and your database is on fire.

Picture a coat check with four counters. Someone opens a fifth, and every coat in the building has to be carried to a new counter. Consistent hashing is the trick that moves only one counter's worth of coats.

Draw a circle. Scramble each server's name into a spot on the circle and pin it there. Scramble each key the same way, drop it on the circle, and walk clockwise until you bump into a pin. That pin's server owns the key.

Add a server and it only steals the keys sitting just before its new pin. Remove one and its keys slide to the next pin along. Nothing else moves. Try it.

Here's the catch. With only a few pins, the gaps between them are lopsided, so one server ends up hoarding keys. And when you remove a server, its entire load dumps onto a single neighbor.

The fix is charmingly dumb: give each server many pins instead of one (called virtual nodes). The gaps even out and a dead server's keys spread across everyone. Drag the slider and watch the bars level off.

It's 1997. Six people at MIT's Laboratory for Computer Science, David Karger, Eric Lehman, Tom Leighton, Rina Panigrahy, Matthew Levine and Daniel Lewin, present a paper at the STOC conference: "Consistent Hashing and Random Trees: Distributed Caching Protocols for Relieving Hot Spots on the World Wide Web".

The problem

The early web had "hot spots": a page gets popular, one server gets crushed. The obvious cure is many caching servers spread across the internet. But the internet has no central manager, and servers come and go constantly, so any scheme that reshuffles everything on each change is dead on arrival.

The naive fix

Hash modulo the number of servers. Fine for a fixed cluster, disastrous the moment the count changes.

The insight

Map servers and keys onto the same circle, so adding or removing a server only touches its neighbors. The paper also shows that clients with slightly different views of which servers exist still mostly agree on where things live.

Since then

Leighton and Lewin turned the idea into a company: Akamai, incorporated in August 1998, built its content delivery network on it. Chord (2001) used the ring for peer-to-peer lookup. Amazon's Dynamo paper (2007) brought it, plus virtual nodes, into databases, and most modern key-value stores followed.

Notice what the trick trades: perfect balance for stability. A plain modulo spreads keys beautifully, but only if nothing ever changes. The ring accepts some lumpiness in exchange for surviving change.

Anywhere a set of machines shares out a set of keys and the machines can't be trusted to stay put.

Dynamo-style databases

Amazon DynamoDB, Apache Cassandra and Riak partition data around a ring with virtual nodes, so a node joining or dying reshuffles only a slice.

Distributed caches

Memcached client libraries pick which cache server holds a key with a ring (the "ketama" scheme, written at Last.fm in 2007 after server changes kept wiping their whole cache), so a cache node outage doesn't flush every other node.

Content delivery networks

Akamai uses consistent hashing inside a cluster to decide which edge server should hold a given piece of content.

What it can't do: it doesn't balance load by itself (hot keys are still hot), and lookups need the sorted pin list, so a plain ring is slower than a modulo. Newer cousins like jump hash and rendezvous hashing trade away the circle to fix that.
